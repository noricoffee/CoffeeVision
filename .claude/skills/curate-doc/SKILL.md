# doc の棚卸し

**棚卸し = 縮約ではない。** 最初に来るのは陳腐化チェック（コードとの突き合わせ）で、行数の削減はその後。順番を逆にすると「古い記述を綺麗に整形する」だけで終わる。

2026-07-25 の data-model.md（1246 行）で 3 段を通し、陳腐化 6 件 + 欠落 2 件 + **無言のデータ欠損バグ 1 件**を検出した。行数だけ見て縮約から入っていたら、そのバグは見つかっていない。

## Phase 0 — 型を見分ける

対象 doc がどれかで、この先の手順が変わる:

| 型 | doc | 閾値 | 手順 |
|---|---|---|---|
| **ストック型の正本** | `data-model` / `analysis-model` / `requirements` / `architecture` / `coding-conventions` / `ui-ux-guidelines` / `kmp-bridge` / `app-store-metadata` / `paid-services` | 500 行 | Phase 1 → 2 →（まだ超えていれば）3 |
| **フロー型** | `tasks.md` / `implementation_note.md` | 1200 行 | **present-tense の節にだけ Phase 1** → Phase 2 →（作業ログは縮約が効かないので）**Phase 3 = 月次アーカイブへ凍結移送**。**規則は各 doc の前文が正本**（tasks: カテゴリ制 + 縮約 / note: 昇格パス + アーカイブ）なのでまず前文を読む |

> **フロー型でも「今こうなっている」と書いてある節は Phase 1 の対象**（2026-08-01 追加）。日付付きエントリは*その時点の記録*なので古くなるのが正常だが、`implementation_note` の「現在生きてる方針サマリ」や `tasks.md` のセクション前文は**現在形で断言している**ため、実装とずれたら普通に嘘になる。しかもこの種の節は doc の冒頭にあって最初に読まれる。2026-08-01 の棚卸しでは、行数が閾値未満（1062 < 1200）でアーカイブ不要だったにもかかわらず、サマリ側から陳腐化 2 件 + 欠落 4 件 + コード側の誤り 1 件が出た。**行数で不要と判断しても、present-tense 節の照合だけは通す。**
| **対象外** | `tasks/lessons.md` / `talks/` | — | 「昇格しても発生源として残す」設計。行数を理由に縮めない |

**完了条件**: 型を特定し、フロー型なら該当 doc の前文を読み終えた。

## Phase 1 — 陳腐化チェック（コードと突き合わせ）

doc を**全文**読み、doc が名指ししている実体（モデル / Repository / スキーマ / 定数 / Rules ファイル / スクリプト）を**すべて開いて**照合する。grep でファイル名の存在確認だけして済ませない — 中身のフィールドと値まで見る。

見つかるものは 3 種類あり、行き先が違う:

- **陳腐化**（doc が実装より古い / 節内で矛盾）→ doc を直す
- **欠落**（実装にあるのに doc に無い表現・モデル）→ doc に足す。行数は増えるが正本の穴なので埋める
- **コード側の誤り**（doc が正しく実装が間違い）→ **`docs/tasks.md` に起票**し、担当サブエージェントへ dispatch する。ここで直接コードを触らない。**Phase 1 を全部終えてから、担当ごとに 1 回にまとめて dispatch する**（1 件ずつ投げると同じ doc を何度も読ませることになる。2026-07-25 は KDoc 修正を 3 回に分けてしまった）

**doc とコードのどちらが正本か、思い込みで決めない。** 逆向きの例がある: `scripts/seed/seed-bean-profiles.mjs` の `FLAVOR_VOCABULARY` は「正本は data-model §3.2」とコメントされており doc が正本。「スクリプトが正だろう」で消すと仕様が失われる。

**完了条件**: doc が名指しする実体を全件照合し、3 種類それぞれの件数を言える（0 件なら 0 件と言える）。

## Phase 2 — 縮約

判定軸は doc の型ではなく **複製か仕様か**。

- **削る = ソースが正本のものの逐語コピー**: SQL クエリ本体 / Rules 全文 / 実装コード / 定数リストの中身 / interface のシグネチャ列挙（→ 箇条書き・表へ）
- **残す = 仕様**: 列定義、公開 API の「形」、フィールドの型と null 許容、不変条件、表現間のマッピング規則、設計上の決め事
- **移す = 経緯・実測値・不採用案** → `implementation_note.md`

内訳を測ると当たりが付く（data-model は 53% がコードブロックだった）。同梱スクリプトで総行数・コードブロック比率・見出しごとの行数が出る:

    .claude/skills/curate-doc/measure-doc.sh <doc>

**コードブロック比率が低い doc（作業ログなど）に縮約は効かない。** その場合は Phase 3 へ回す。

**移す前に受け皿の存在を grep で確認する。** 既に implementation_note にあるなら「移動」ではなく「doc 側を結論 + 参照に置換」。無いなら先に受け皿を書く。**確認せず消すのは削除**であって棚卸しではない。

doc 内のコード複製は、それ自身が追随コストの発生源。過去に doc のサンプルだけが実体と乖離して修正タスクになった実例が 2 件ある（tasks #6 / #7）。削る判断の後押しに使える。

**完了条件**: 削った各ブロックについて「正本はどのファイルか」を doc 内に書いた。移した各記述について受け皿での存在を確認した。

## Phase 3 — 分離（Phase 2 後もまだ大きいとき）

**分離軸は性質で切る**（章の順番や行数バランスで切らない）。実績のある 2 つの軸:

- **永続するか否か** — data-model → analysis-model（永続しない派生集計は更新契機が違う）
- **追記が止まったか否か** — 作業ログ（`implementation_note` / `tasks`）→ `docs/archive/<version>/`（**完了して凍結した月・リリース済みのバージョン**を切る。append-only 気味に伸びるので、縮約で閾値に収めようとすると経緯そのものを削る = 歴史の破棄になる）。**移送は逐語で行い、`diff` で本文一致を確認してからコミットする**（縮約を混ぜると逐語性を検証できなくなるので、移送と内容変更はコミットを分ける）。凍結先は行数閾値の対象外（`check-file-size.sh` が `docs/archive/*` を除外）

参照の壊し方に 2 つの規律がある:

- **既存 doc の節見出しは削除・改番しない。** 欠番が空くのは許容し、意図的であることを doc に明記する（他 doc / コードから名指しされている番号を動かす方がコストとリスクが高い）
- **旧番号にリダイレクト表を残す。** これがあると、**完了済みタスク行・変更履歴のような「史実としての参照」は書き換えずに済む**（当時そこに書いたという記録を改変しない）。張り替えるのは「現在の正本の場所を指す live pointer」だけ

新 doc は**独自採番**にする（移動元の番号を引き継ぐと新規読者に意味不明な番号が残る）。

コード内の参照（KDoc / コメント）は親のスコープ外なので **`kmp-engineer` / `ios-engineer` に dispatch** する。片方の doc に残る節と移動する節を同時に参照している箇所（例: `§1.3a` は残留・`§1.6` は移動）は張り替えで壊しやすいので、dispatch 時に明示する。

**完了条件**: `CLAUDE.md` 必読表と `docs/README.md` に新 doc を登録し、下記の検証を通した。

## 全 Phase 共通の締め

1. **名指し参照の生存検証**（このリポジトリはアンカーリンク不使用・参照は本文名指し）。節番号を機械照合する:

   ```bash
   # doc 側の実在節番号を集め、全参照（docs / *.kt / *.swift）と突き合わせて dangling を出す
   grep -rn --include='*.md' --include='*.kt' --include='*.swift' '<doc名>' . | grep -v '/build/' | grep -oE '§[0-9]+(\.[0-9]+[a-z]?)?'
   grep -nE '^#{1,3} [0-9]' <doc>
   ```

2. **同名別 doc の節番号を誤爆させない**: `data-model.md §1.7` と `coding-conventions.md §1.7` は別物。張り替えの判定は「同じ文が指している doc 名」で行う
3. **markdown の機械検査**: code fence の対応（偶数）とテーブルの列数整合
4. **doc にコードの行番号を書かない**（`Foo.swift:1383` 等）。リファクタで即壊れる — 2026-07-25 に実際に壊れているのを検出した。ファイル名か型名で指す
5. **doc の前文に運用ルールを明文化する** — 次回の判断基準を doc 自身に残す。棚卸しの中身を skill と doc に二重化せず、**doc 固有の基準は doc の前文が正本**
6. **チェックポイントコミット 2 段**: 現状コミット → 適用 → 別コミット（ユーザーの明示指示）
7. **判断の経緯を `implementation_note.md` に記録**。汎用的な落とし穴が出たら `record-lesson` skill へ
