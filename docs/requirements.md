### 2. CoffeeRecord（コーヒー記録）管理

CoffeeRecord は **1 杯のコーヒー = 1 件の記録**を表すアプリの中心エンティティ。カフェで飲んだ 1 杯にも、自宅などでのセルフ抽出にも対応する（カフェ情報は任意）。

> **設計変更（2026-07-01 反映）**: 初期設計では「1 回の訪問（`Visit`）に複数の `CoffeeItem` / `FoodItem` がぶら下がる」ネスト構造だったが、実装では **1 杯 = 1 記録のフラットな `CoffeeRecord`** に統合済み。コーヒー属性は記録本体へ昇格し、`CoffeeItem` / `FoodItem` は廃止。フード・内装の雰囲気などは自由メモ（`notes`）へ吸収する。経緯・詳細は [`data-model.md`](./data-model.md) §1.1。

**CoffeeRecord フィールド**

| フィールド | 型 | MVP | 備考 |
|----------|---|-----|------|
| カフェ情報 | `Cafe?`（Places API 由来） | ◎ | place_id・名称・住所・座標・写真参照などをスナップショット保存。**null = セルフ抽出（自宅等）** |
| 飲んだ日 | `LocalDate` | ◎ | デフォルトは今日 |
| 総合評価 | `Double?`（0.5 刻み、0.5..5.0） | ◎ | UI は星 5 段階（ハーフ対応）。**`null` = 未評価**（集計から除外）。**未評価のまま保存可**（「まず記録、あとで評価」）。2026-07-12 B-4 で 0.0 sentinel から nullable 化 |
| メモ | `String`（複数行） | ◎ | 風味・所感・フード・内装の雰囲気などを自由記述（旧 ambiance / FoodItem を吸収） |
| 写真 | 複数の `Photo` | ◎ | 端末ローカル（Documents 配下）に保存。iCloud Backup でバックアップ。**1 記録あたり最大 10 枚**、保存時に**長辺 2048px / JPEG q0.8 へ縮小**（2026-08-01 確定。根拠は未決事項の該当行） |
| コーヒー名 | `String` | ◎ | 「本日のコーヒー」「エチオピア イルガチェフェ」など（必須） |
| 抽出方法 | `enum BrewMethod` | ◎ | エスプレッソ / ハンドドリップ / ネルドリップ / フレンチプレス / エアロプレス / サイフォン / コールドブリュー / その他 |
| 産地 | `String?`（国名） | ◎ | **国ドロップダウン選択**（`CoffeeOriginCatalog` = コーヒー生産国 ~43 か国 + 「ブレンド」/「その他」）。入力の手間削減のため 2026-07-22 に自由入力から変更。「その他」は国名の自由入力欄を出す。詳細 [`data-model.md`](./data-model.md) §1.3a |
| エリア | `String?`（自由入力） | ○ | 農園 / 生産地域（例「イルガチェフェ」「ウエウエテナンゴ」）。産地（国）から分離（2026-07-22）。表示専用で分析には使わない |
| 品種 | `String?`（自由入力 + 推奨候補） | ○ | ティピカ / ブルボン / ゲイシャ / SL28 等 |
| 精製方法 | `enum ProcessingMethod?` | ○ | ナチュラル / ウォッシュト / ハニー / アナエロビック / その他 |
| 焙煎度 | `enum RoastLevel?` | ◎ | ライト / シナモン / ミディアム / ハイ / シティ / フルシティ / フレンチ / イタリアン |
| カップ | `String?`（使用されたカップの種類 / ブランド等のメモ） | ○ | |
| 抽出レシピ | `String?`（豆量 / 湯量 / 湯温 / 抽出時間などのメモ） | △ | セルフ抽出向け（2026-07-06 起票）。構造化フィールド化は実装時に判断、当面は `notes` 吸収でも可 |
| テイスティング | `TastingScores?`（甘味 / ボディ / 酸味 / 風味 / 後味、各 1..10） | ○ | Blue Bottle「Elements of Coffee Tasting」由来のテイスティング 5 要素。強度スケール（UI はスライダー）。**任意だが、付ける場合は 5 要素すべて必須**（all-or-nothing）。`+` で 5 スライダーを一括表示。詳細は [`data-model.md`](./data-model.md) §1.1a |
| タグ | `List<String>` | ○ | ユーザー定義タグ（例: 「ラテアート」「浅煎り」） |

### 5. カフェ検索（Google Places API）

> **帰属表示の義務（2026-08-07 追加）**: Places のコンテンツを **Google マップ以外**（本アプリは Apple MapKit + 自前 UI）に表示する場合、Google Maps ロゴ（スペースが限られる場合は「Google Maps」テキスト）の表示がポリシー上必須。さらに**写真は表示のたびに作者をクレジット**する必要がある（`Cafe.photoAttributions`、data-model §1.2）。App Store ガイドライン 5.2.2（サードパーティ規約の遵守）に直結し、審査より **Google 側の是正要求 → API キー停止**のほうがリスクが大きい。**Places データを新しい画面に出すときは帰属表示をセットで実装すること**。出典: [Places ポリシー](https://developers.google.com/maps/documentation/places/web-service/policies)（2026-08-07 に一次確認）

| # | 機能 | 優先度 | 備考 |
|---|------|--------|------|
| 5-1 | テキスト検索（店名 / キーワード） | ◎ | Places API Text Search |
| 5-2 | 現在地周辺のカフェ検索 | ◎ | Nearby Search、`type=cafe` |
| 5-3 | カフェ詳細（住所・写真・営業時間） | ◎ | Place Details |
| 5-4 | カフェのスナップショットを CoffeeRecord に紐付けて保存 | ◎ | Places API 規約に従い、画像 URL は逐次再取得。セルフ抽出記録は紐付けなし（`cafe = null`） |
| 5-5 | 表示範囲のカフェをマップにピン一括表示（「このエリアを検索」） | ○ | 地図をパン/ズーム後に出るボタンで表示範囲（中心 + 半径）を検索し候補を全ピン表示。Google Maps 風。**検索バーにキーワードがあればそのキーワード + 表示範囲の位置バイアスで再検索（`searchText`）、空なら周辺一括検索（`searchNearby`）**（2026-07-24 改訂。従来はキーワード非依存の周辺検索固定だった）。エリア検索の結果は**検索実行時の表示範囲（可視領域の矩形）内に限定**する（iOS クライアント側フィルタ。`locationBias` は範囲制限でなく近傍ヒントのため範囲外が混入するのを除外。2026-07-24）。Places API の 1 回最大 20 件が上限（範囲外分をクライアントで捨てるため範囲内表示は 20 件未満に減る場合あり）。テキスト検索結果は全件ピン + リスト併用（範囲フィルタ対象外）。フェーズ 14 |
| 5-6 | 都道府県別おすすめカフェの常時強調表示（キュレーション） | ○ | フェーズ 19。サービス管理の Firestore `curatedCafes`（初期スコープ = 東京: 基準上位 100 件 + 人気枠（評価 3.7 以上 & レビュー 500 件以上、枠外全件）、他県は将来 20〜30 件）を専用ピン（通常カフェピンと同アイコンの拡大 + `Color.orange` 高彩度 = Google Maps 風 POI 強調。2026-07-18 に star 意匠から変更）で**トグルなしで強調表示**。表示は Apple 周辺ピンと同じズームゲート（可視半径 3000m 以内）でズームイン時のみ（引きの地図では非表示 — 2026-07-18 常時表示から改訂）。Google Maps の POI 強調のイメージ。タップで placeId 直渡しのカフェ詳細へ（Details 1 回で解決）。一覧シート・チップは作らない。詳細は [`data-model.md`](./data-model.md) §1.10 |

### 9. 分析（コーヒー傾向分析）

これまで登録した `CoffeeRecord` 群を分析し、自分の好み・傾向を振り返るための機能。専用の「分析」タブとして提供する。分析は **3 階層** で構成する（詳細設計は [`implementation_note.md`](./implementation_note.md) 2026-06-19 分析機能エントリ / 集計モデルは [`analysis-model.md`](./analysis-model.md) §1）。

| 階層 | 内容 | 計算方法 | プラットフォーム |
|------|------|---------|----------------|
| 1. 記述統計 | 杯数 / 産地分布 / 焙煎度・抽出方法分布 / 平均評価 / 月次推移 / よく行く店 | KMP 共通層で決定論的に算出（`CoffeeStats`） | iOS / Android 共通（表示は iOS のみ） |
| 2. 傾向抽出 | 高評価群（rating ≥ 4.0）に共通する属性を最小サンプル数の閾値付きで抽出 | KMP 共通層でルールベース算出（`FavoriteSignals`） | 同上 |
| 3. 自然言語の解釈 | 階層1・2 の集計サマリを基に「あなたの傾向」を要約 / 対話 Q&A で応答 | iOS の Foundation Models（オンデバイス LLM） | **iOS 専用**（Android は分析タブ非表示） |

**設計原則**: 数値・分布は階層1・2 で**決定論的に正確に**算出し、その**集約済みサマリ（`CoffeeStats`）だけ**を階層3 の LLM に渡す。生レコードを LLM に流さない（正確性 / オンデバイス LLM のコンテキスト窓 / 再現性・テスト容易性のため）。

| # | 機能 | 優先度 | 備考 |
|---|------|--------|------|
| 9-1 | 記述統計の可視化（階層1） | ○ | 杯数・産地・焙煎度・抽出方法・平均評価・月次推移・よく行く店・**テイスティング 5 要素の平均**（甘味/ボディ/酸味/風味/後味） |
| 9-2 | Foundation Models による傾向要約サマリ（階層3） | ○ | `CoffeeStats` を入力に 2–3 文で要約。Apple Intelligence 無効 / 非対応端末では階層1 のみ表示にフォールバック |
| 9-3 | 高評価群の傾向抽出（階層2） | △ | `FavoriteSignals`。サンプル数が閾値未満の信号は出さない |
| 9-4 | 対話 Q&A v1（階層3 / 単発・digest 文脈注入） | ○ | 「好きな産地は？」「一番高評価だったコーヒーは？」等を **1 問 1 答（ステートレス）** で回答。`CoffeeStats` digest のみを文脈注入（生レコード・tool 無し / 計算は KMP、LLM は解釈と整形のみ）。digest に無い問いは「記録からは分かりません」。非対応端末（Apple Intelligence 無効）は Q&A UI 非表示。逐次表示なし（suspend 一発） |

### 11. 広告（AdMob アダプティブバナー）

収益化手段として Google Mobile Ads SDK（AdMob）の**アダプティブバナー広告**を表示する（2026-07-14 grilling で確定）。Places API を主とする従量コストの回収が目的。

> **フォーマット変更の経緯（2026-07-14 同日）**: 当初は「UI に溶け込む」を優先しネイティブ広告で確定・実装したが、テスト広告の validator で **MediaView（最小 120×120pt）が必須アセット**と判明。コンパクト枠（ドロップダウン行 / 下部固定枠）に 120pt のメディアを組み込むとバナー（50〜60pt）より大きく悪目立ちし、「溶け込むからネイティブ」の前提が崩れたため、**全面アダプティブバナーに再編**（ユーザー確定）。経緯は implementation_note 2026-07-14。
>
> **記録・分析タブの撤去（2026-07-16）**: ユーザビリティレビューで「個人の記録・振り返り画面（定着の核）に置くバナーは、定着が命の初期にリテンションを削る割に収益が小さい」と判断し、11-3 の 2 面を**一度撤去**（ユーザー確定。再導入の余地は残す — コンポーネントは git 履歴から復元可能）。広告は 11-1 カフェ詳細 / 11-2 マップ検索ドロップダウンの 2 面のみとなる。ATT フロー（11-4）は残存 2 面のため維持。経緯は implementation_note 2026-07-16。

**アーキテクチャ上の位置づけ**: 広告は表示の関心事として **`iosApp` の View 層で完結**させ、KMP 共通層・ViewModel には広告の概念を持ち込まない。Android（KMP 検証ターゲット、リリース対象外）には導入しない。将来の「広告非表示」IAP は**見据えない**（必要になった時点で後付けする。2026-07-14 判断）。

| # | 機能 | 優先度 | 備考 |
|---|------|--------|------|
| 11-1 | カフェ詳細のインライン広告 | ○ | 情報系セクション（カフェ情報 / 外部リンク / 営業時間）の後・コーヒー記録セクションの直前に 1 枠。**インラインアダプティブバナー**（maxHeight 制限付き） |
| 11-2 | マップ検索結果シートのインライン広告 | ○ | 検索結果シート（下部ドラッグシート、2026-07-22）内の 3 件目の後に 1 枠。**結果 3 件未満のときは非表示**（広告が結果を支配するのを避ける）。**インラインアダプティブバナー**（maxHeight 制限付き）。旧・上部ドロップダウン提示から移設（配置ルール不変） |
| 11-3 | コーヒー記録タブ / 分析タブの広告 | ✕（2026-07-16 撤去） | リスト先頭インライン / 下部固定（maxHeight 90）で実装・表示確認まで完了したが、定着優先で一度撤去（上記「記録・分析タブの撤去」注記）。配置変遷の経緯は implementation_note 2026-07-14〜15 |
| 11-4 | ATT 許可フロー（プレプロンプト付き） | ○ | 既存のデータ利用同意オンボーディング直後に「広告により無料で提供している」旨の説明（プレプロンプト）→ ATT ダイアログ。拒否時は非パーソナライズ広告（NPA）にフォールバック。**未実施ユーザーは起動時（`bootstrap()` 完了時）に 1 回だけ到達させる**（`UserDefaults` フラグ方式。オンボーディング済みの既存ユーザーの取りこぼし防止。implementation_note 2026-07-14） |

**確定仕様（全面共通）**:

- ロード失敗・オフライン時は**枠ごと畳む**（プレースホルダなし。補助機能の失敗は無音の既存方針と整合）
- クライアント側の自動リフレッシュ実装はしない（バナーの自動更新は AdMob コンソールのユニット設定に委ねる）
- `maxAdContentRating = G`（全年齢向けに制限）
- AdMob App ID / 広告ユニット ID（2 面 = 2 ユニット、**バナー用**。2026-07-16 の 11-3 撤去で 4 → 2）は Places キーと同じ経路（`Secrets.xcconfig` → `Info.plist`）で注入
- 広告の帰属表示・AdChoices はバナーでは Google レンダリングに内蔵されるため自前実装なし
- 配信地域は**日本のみ**（確定）→ GDPR 同意フォームは不要。**UMP のメッセージ表示 API はコードから呼ばない**（コンソール構成に挙動が依存し、ATT メッセージ構成時は GDPR 圏外でも自前プレプロンプトと二重表示になるため。UMP SDK 自体は Google Mobile Ads SDK の内部依存としてリンクされるのみ。EU 配信を始める場合は GDPR フォーム実装として再導入。implementation_note 2026-07-14）
- **Places 由来のデータ（店名・カテゴリ等）を広告リクエストのターゲティングシグナルに渡さない**（Google Maps Platform 規約遵守）

**未決事項**: 広告のプリロード / セッション内キャッシュ戦略の詳細は実装時に判断。
