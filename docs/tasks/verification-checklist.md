## 実行順の設計

**トピック別ではなく前提条件別に並べる**。理由は、目視項目の多くが「一度きりしか観察できない状態」に依存しているため。

- **初回起動フローは 1 インストールにつき 1 回**しか見られない（同意オンボーディング / 広告プレプロンプト / ATT）
- **許可ダイアログは許可を出した瞬間に消える**。位置情報を許可する前・写真を許可する前にしか確認できない項目がある
- **記録 0 件の空状態**は記録を 1 件作った時点で失われる

トピック順に上から消化すると、これらを見落として**再インストールをやり直す**ことになる。以下の順なら**再インストールは 2 回**（パス 1 とパス 7）で全項目を消化できる。

| パス | 前提 | 内容 |
|------|------|------|
| 1 | **削除 → 再インストール**（1 回目） | 初回起動フローと空状態。**許可を出す前**の挙動を先に取る |
| 2 | なし | 記録の作成・編集・複製・削除。項目数が最も多い |
| 3 | Location 設定 + 実 Places キー | マップ / カフェ探索 |
| 4 | 記録が数件たまった状態 | 分析タブ |
| 5 | ダミーデータ Scheme | 30 件が要る項目 |
| 6 | **実機**（シミュレータ不可） | Apple Intelligence / Sign in with Apple / 長時間利用 |
| 7 | **削除 → 再インストール**（2 回目） | レビュー依頼の 1 回きり挙動とキルスイッチ |
| 8 | 後日 | Firebase コンソールの観察 |
| 9 | 通し | アクセシビリティ |

**パス 1 の中も順序が意味を持つ**。①同意オンボーディング → ②位置情報を許可する前にエディタを開く → ③記録 0 件の空状態 → ④初回の写真追加（許可ダイアログ）→ ⑤ここで各種許可を出してパス 2 へ。

**共通の前提**:

- 位置情報に依存する項目はシミュレータの **Features > Location（Custom Location）設定**が前提（未設定だとサジェスト等が出ない — lessons 2026-07-06）
- 広告・Remote Config 依存はテスト ID / デモユニットでの確認になる（`No fill` はコード無罪の可能性 — implementation_note 2026-07-22）

## パス 2: 記録の作成・編集・複製（前提なし）

- [ ] **各画面の更新が従来どおり追従すること**（SL-3）。ブリッジ 8 本の `apply(_:)` に同値ガードを入れて**通知の回数を減らした**ため、退行するなら「更新されない」形で出る。記録一覧 / 記録詳細 / カフェ詳細 / 分析タブ / カフェ検索を一通り。**特に記録エディタの文字入力の追従**（`tagInput` / `draft` の echo が遅れたり取りこぼしたりしないか）

- [ ] **共有カードの share sheet が `ShareLink` 版から劣化していないこと**（1.0.1 / ASO-7②-a）。記録詳細 → 共有ボタン → プレビュー → 「共有する」。`ShareLink` を `UIActivityViewController`（`ActivityShareSheet`）へ置き換えたため、**share sheet 上部のプレビュー（サムネイル + タイトル）を `LPLinkMetadata` で作り直している**。ここが素っ気なくなっていないかが最大の確認点
- [ ] **共有先に画像とテキストの両方が渡ること**（1.0.1 / ASO-7②-a）。X / LINE / メモ等へ実際に共有し、**カード画像 + 本文 2 行**（`{コーヒー名} - CoffeeVision` / `https://apps.apple.com/app/id6788339362`）が入ること。**URL がタップ可能なリンクになるか**も見る（X は画像添付時にリンクプレビューのカードを出さないが、リンク自体は生きるのが期待挙動）
- [ ] **共有ボタンを押してから share sheet が出るまでが引っかからないこと**（1.0.1）。PNG エンコードとファイル書き込みを `@concurrent` でメインスレッドから外した効果の体感確認。**写真付きの記録**（エンコード量が多い）で見る

## パス 3: マップ / カフェ探索（Location 設定 + 実 Places キー）

> **以下 4 件は Swift 言語設計レビュー（SL-4 / SL-9 / SL-10）由来**。マップのピン競合解決を `MapTabView` の body から `MapViewModelBridge` へ移し、カメラ合わせを `MapRegionFitting` に括り出したため、**描画結果は同じはずだが計算タイミングが変わっている**。設計判断は [`implementation_note.md`](../implementation_note.md) 2026-09-20。

- [ ] **5 種のピンが従来と同じ集合・同じ優先順位で出ること**（SL-4）。訪問済み / 保存済み / 検索結果 / おすすめ（オレンジ）/ Apple 周辺（低強調）。**同一店舗が 2 種類のピンで二重表示されないこと**が最大の確認点（競合解決の除外ロジックをブリッジ側へ移設したため）
- [ ] **おすすめピンのズームゲートと先読みが効くこと**（SL-4）。ズームアウトで消え、ズームインで戻る（可視半径 3000m）。パンしたとき画面端でピンが遅れて出ないこと（可視範囲マージン 1.3 倍）。**カメラ中心の受け渡し経路が `.onMapCameraChange` → ブリッジへ変わった**ので、ここが壊れていると「ピンが出ない / 出っぱなし」になる
- [ ] **起動直後に Apple 周辺ピンが訪問済み / 保存済みピンと重なって残らないこと**（SL-4）。**既知のトレードオフとして 1 フレーム分の遅延がある** — 重複排除の入力がブリッジ経由になったため、新しいピンが出た直後の 1 パスだけ 40m 以内に Apple ピンが重なりうる（次のパスで消える）。**「一瞬重なって即消える」なら許容、「重なったまま残る」なら不合格**
- [ ] **カメラフィットが 0 / 1 / 複数件の 3 ケースで従来どおりであること**（SL-9）。①位置情報を**拒否**した状態で訪問済みカフェ 0 件 = 東京駅 5km / 1 件 = 2km / 複数件 = bounding box ②テキスト検索の結果 1 件 = 800m / 複数件 = bounding box。**計算を `MapRegionFitting` へ括り出した際に単一件数のズーム距離差（2000m / 800m）を引数化してある**ので、ここが取り違わっていないか
- [ ] **現在地 FAB の連続タップで再センタリングが効くこと**（SL-10）。`lastLocation` に同値ガードを入れたため。理屈上は無影響（消費側はすべて `.onChange` 経由）だが、**「2 回目以降が効かない」形の退行が出るならここ**

- [ ] **`CafeSelectionCard` の情報行が狭幅端末で破綻しないこと**（1.0.1 / 営業状態の文言統一）。営業状態を「終了」→「営業時間外」に統一した結果、**バッジ行の幅予算を超えうる**。`.lineLimit(1)` を入れてあるので行が複数行化してカードが崩れることはなく、代わりに末尾が `…` で切り詰められる。**どのバッジが削られるかは SwiftUI の縮小挙動次第で机上では確定できない**ため目視が要る。
  - **見るべき最悪ケース**: 4 バッジが同時に揃うカフェ（営業時間データあり + 評価件数 3 桁 + 価格帯 `¥¥¥¥` + 訪問記録あり）を**iPhone SE クラス（375pt 幅）**で表示する
  - **実測値**（サブエージェントが `NSAttributedString.size()` で計測 / 2026-08-21）: `.caption` で「終了」22.2pt →「営業時間外」55.4pt。行合計は 198pt → 231pt に対し、情報行の利用可能幅は SE ≈ 211pt / 393pt 級 ≈ 229pt。**変更前から余白は 13pt しかなく、SE では超過する見込み**
  - **「営業時間外」自体が `…` で切れていたら不合格**（優先度が最も高いバッジのため）。その場合は文言の再検討（例: 「営業終了」＝ 4 文字）か情報行の 2 行化を親が判断する

## パス 6: 実機必須（シミュレータ不可）

- [ ] **サインアウト → 再サインインを 2〜3 回繰り返して同期が毎回正常なこと**（SL-1）。**これが SL-1 の唯一の実地検証**。Firestore / Auth のリスナハンドルをロック保護に移したのは「解除が飛ばずリスナが積み上がる」経路を塞ぐためで、症状は「壊れる」ではなく「残る」形で出る。各サイクル後に記録一覧・マップ・カフェ保存・設定の同意トグルがすべて正常に更新されること
- [ ] **ログに uid が `<private>` と伏せられること**（SL-8）。**デバッガを外した実機 / TestFlight ビルド**で Console.app またはデバイスログを見る。**シミュレータでは実証できない**（デバッガ配下では private データがそのまま表示される Apple の挙動）。`print` からの移行で `privacy: .private` を付けた対象は uid / LLM ツールの検索条件 / ユーザー発話由来の自由文（一覧は implementation_note 2026-09-20）

> **`AccountView` の項目はこのパスの最後に回す**。アカウント削除・サインアウトは**それまでに積んだ状態を壊す**ため、他の項目を消化しきってから実行する。ここで消えた状態はパス 7 の再インストールでどのみち失われるので、順序上の損はない。再認証に Sign in with Apple を伴うため実機必須。

- [ ] **処理中に「戻る」の全経路が塞がること**（1.0.1 / SR-1 残務）。サインアウトまたはアカウント削除の実行中に、①ナビゲーションバーの**戻るボタンが消えている** ②**画面左端からのエッジスワイプで戻れない** ③「完了」ボタンが無効。**②が本命**（`.navigationBarBackButtonHidden` では止まらないため `InteractivePopGestureLock` を新設した箇所）
- [ ] **処理完了後に戻るが復帰すること — 成功時と失敗時の両方**（1.0.1）。**失敗時に解除されないと画面から出られなくなり、封じる前より悪い退行**になる。機内モード等で通信を落として失敗させ、エラーアラートを閉じた後に戻れることを確認する
- [ ] **`AccountView` のナビゲーションバーが崩れていないこと**（1.0.1）。入れ子 `NavigationStack` を外して `SettingsView` 側のスタックに統合したため、**二重ナビゲーションバー・タイトルの重複・ツールバーの位置ずれ**が無いかを見る
