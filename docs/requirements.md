### 2. CoffeeRecord（コーヒー記録）管理

CoffeeRecord は **1 杯のコーヒー = 1 件の記録**を表すアプリの中心エンティティ。カフェで飲んだ 1 杯にも、自宅などでのセルフ抽出にも対応する（カフェ情報は任意）。

> **設計変更（2026-07-01 反映）**: 初期設計では「1 回の訪問（`Visit`）に複数の `CoffeeItem` / `FoodItem` がぶら下がる」ネスト構造だったが、実装では **1 杯 = 1 記録のフラットな `CoffeeRecord`** に統合済み。コーヒー属性は記録本体へ昇格し、`CoffeeItem` / `FoodItem` は廃止。フード・内装の雰囲気などは自由メモ（`notes`）へ吸収する。経緯・詳細は [`data-model.md`](./data-model.md) §1.1。

**CoffeeRecord フィールド**

| フィールド | 型 | MVP | 備考 |
|----------|---|-----|------|
| カフェ情報 | `Cafe?`（Places API 由来） | ◎ | place_id・名称・住所・座標・写真参照などをスナップショット保存。**null = セルフ抽出（自宅等）** |
| 飲んだ日 | `LocalDate` | ◎ | デフォルトは今日 |
| 総合評価 | `Double?`（0.5 刻み、0.5..5.0） | ◎ | UI は星 5 段階（ハーフ対応）。**`null` = 未評価**（集計から除外）。**未評価のまま保存可**（「まず記録、あとで評価」）。2026-07-12 B-4 で 0.0 sentinel から nullable 化 |
| メモ | `String`（複数行） | ◎ | 風味・所感・フード・内装の雰囲気などを自由記述（旧 ambiance / FoodItem を吸収） |
| 写真 | 複数の `Photo` | ◎ | 端末ローカル（Documents 配下）に保存。iCloud Backup でバックアップ |
| コーヒー名 | `String` | ◎ | 「本日のコーヒー」「エチオピア イルガチェフェ」など（必須） |
| 抽出方法 | `enum BrewMethod` | ◎ | エスプレッソ / ハンドドリップ / ネルドリップ / フレンチプレス / エアロプレス / サイフォン / コールドブリュー / その他 |
| 産地 | `String?`（国名 / エリア） | ◎ | 豆ナレッジ（`BeanProfile`）由来のサジェストあり（フェーズ 12-B） |
| 品種 | `String?`（自由入力 + 推奨候補） | ○ | ティピカ / ブルボン / ゲイシャ / SL28 等 |
| 精製方法 | `enum ProcessingMethod?` | ○ | ナチュラル / ウォッシュト / ハニー / アナエロビック / その他 |
| 焙煎度 | `enum RoastLevel?` | ◎ | ライト / シナモン / ミディアム / ハイ / シティ / フルシティ / フレンチ / イタリアン |
| カップ | `String?`（使用されたカップの種類 / ブランド等のメモ） | ○ | |
| 抽出レシピ | `String?`（豆量 / 湯量 / 湯温 / 抽出時間などのメモ） | △ | セルフ抽出向け（2026-07-06 起票）。構造化フィールド化は実装時に判断、当面は `notes` 吸収でも可 |
| テイスティング | `TastingScores?`（甘味 / ボディ / 酸味 / 風味 / 後味、各 1..10） | ○ | Blue Bottle「Elements of Coffee Tasting」由来のテイスティング 5 要素。強度スケール（UI はスライダー）。**任意だが、付ける場合は 5 要素すべて必須**（all-or-nothing）。`+` で 5 スライダーを一括表示。詳細は [`data-model.md`](./data-model.md) §1.1a |
| タグ | `List<String>` | ○ | ユーザー定義タグ（例: 「ラテアート」「浅煎り」） |

### 9. 分析（コーヒー傾向分析）

これまで登録した `CoffeeRecord` 群を分析し、自分の好み・傾向を振り返るための機能。専用の「分析」タブとして提供する。分析は **3 階層** で構成する（詳細設計は [`implementation_note.md`](./implementation_note.md) 2026-06-19 分析機能エントリ / 集計モデルは [`data-model.md`](./data-model.md) §1.6）。

| 階層 | 内容 | 計算方法 | プラットフォーム |
|------|------|---------|----------------|
| 1. 記述統計 | 杯数 / 産地分布 / 焙煎度・抽出方法分布 / 平均評価 / 月次推移 / よく行く店 | KMP 共通層で決定論的に算出（`CoffeeStats`） | iOS / Android 共通（表示は iOS のみ） |
| 2. 傾向抽出 | 高評価群（rating ≥ 4.0）に共通する属性を最小サンプル数の閾値付きで抽出 | KMP 共通層でルールベース算出（`FavoriteSignals`） | 同上 |
| 3. 自然言語の解釈 | 階層1・2 の集計サマリを基に「あなたの傾向」を要約 / 対話 Q&A で応答 | iOS の Foundation Models（オンデバイス LLM） | **iOS 専用**（Android は分析タブ非表示） |

**設計原則**: 数値・分布は階層1・2 で**決定論的に正確に**算出し、その**集約済みサマリ（`CoffeeStats`）だけ**を階層3 の LLM に渡す。生レコードを LLM に流さない（正確性 / オンデバイス LLM のコンテキスト窓 / 再現性・テスト容易性のため）。

| # | 機能 | 優先度 | 備考 |
|---|------|--------|------|
| 9-1 | 記述統計の可視化（階層1） | ○ | 杯数・産地・焙煎度・抽出方法・平均評価・月次推移・よく行く店・**テイスティング 5 要素の平均**（甘味/ボディ/酸味/風味/後味） |
| 9-2 | Foundation Models による傾向要約サマリ（階層3） | ○ | `CoffeeStats` を入力に 2–3 文で要約。Apple Intelligence 無効 / 非対応端末では階層1 のみ表示にフォールバック |
| 9-3 | 高評価群の傾向抽出（階層2） | △ | `FavoriteSignals`。サンプル数が閾値未満の信号は出さない |
| 9-4 | 対話 Q&A v1（階層3 / 単発・digest 文脈注入） | ○ | 「好きな産地は？」「一番高評価だったコーヒーは？」等を **1 問 1 答（ステートレス）** で回答。`CoffeeStats` digest のみを文脈注入（生レコード・tool 無し / 計算は KMP、LLM は解釈と整形のみ）。digest に無い問いは「記録からは分かりません」。非対応端末（Apple Intelligence 無効）は Q&A UI 非表示。逐次表示なし（suspend 一発） |
| 9-4b | 対話 Q&A v2（tool calling / 生レコード参照） | ○ | digest で答えられない**個別レコード単位**の問い（特定カフェ・特定月・産地別の個別記録等）向けに、Foundation Models の `Tool` で KMP の生レコード照会（`CoffeeRecordQuery.searchRecords`）を呼ぶ。絞り込みは KMP 側（計算は KMP・LLM は呼び出し判断と整形のみ）。digest はベース文脈として併用（ハイブリッド）。可否判定は v1 と共有（`CoffeeInsightProvider != null` の端末のみ）。インターフェース・設計は [`data-model.md`](./data-model.md) §1.6「対話 Q&A v2」、ブリッジは [`kmp-bridge.md`](./kmp-bridge.md) |
| 9-5 | 好みのカフェをマップで探す（味覚プロファイル一致 / コンテンツベース v1） | △ | `FavoriteSignals` のカテゴリ好み（産地/焙煎/抽出）に一致する高評価記録（rating ≥ 4.0）があるカフェを「あなた好みの一杯があった店」としてマップ上で強調＋理由表示。集計は KMP 共通層で決定論的（`CafeRecommendationProvider` のローカル実装 = `ObserveTasteMatchedCafesUseCase`）。設計は [`data-model.md`](./data-model.md) §1.7、経緯は [`implementation_note.md`](./implementation_note.md) 2026-06-22 B-4 エントリ。**将来の協調フィルタリング（好みが近い他ユーザーの高評価カフェ提案）は同 interface の差し替えで追加**（下記 Future Direction） |
| 9-6 | 協調フィルタリング推薦（好みが近い他ユーザーの高評価カフェ） | ✕（将来 / Future Direction） | 横断ベクトル類似はサーバ側（GCP 等。初期は Firestore KNN / Cloud Function で十分）で計算し、`CafeRecommendationProvider` のリモート実装として差し込む。プロファイルベクトルは `tastingAverages`（5 軸）が基盤。Foundation Models は端末で推薦理由を言語化する一点に限定（類似度計算には使わない）。**本体の難所は計算でなく横断データ基盤＋同意フロー**。詳細は [`implementation_note.md`](./implementation_note.md) 2026-06-22 Future Direction エントリ |
| 9-7 | 分析タブの空状態プログレス | ○ | 傾向信号が出るまでの残り件数を表示（「あと N 杯記録すると傾向が見えます」）。閾値は `FavoriteSignals.minSampleSize`（3）/ `CORRELATION_MIN_SAMPLE`（5）由来。記録継続の動機付け（2026-07-06 起票） |
| 9-8 | 未経験の豆への探索提案 | △ | `FavoriteSignals` × `BeanProfile` で「好みの産地・精製に近い未経験の豆」を提案（12-C 突合の応用、サーバー不要）。9-5 が既訪問店の再訪推薦であるのに対し、こちらは新規開拓のナッジ（2026-07-06 起票） |

> Foundation Models は **iOS 専用**のため、Android（KMP 検証ターゲット）では分析タブ自体を表示しない。階層1・2 の集計（`CoffeeStats` / `BuildCoffeeStatsUseCase`）は KMP 共通層に置き、両 OS でビルド・テスト可能とする。

### 10. 行きたい店リスト（ウィッシュリスト）

見つけた店を保存して再訪につなげる機能（2026-07-06 起票）。記録（訪問済み）とは独立した「これから行く店」の管理であり、「探す → 保存 → 訪問 → 記録」のループを閉じる。エンティティは `SavedCafe`（`Cafe` スナップショット埋め込み + 保存日時 + メモ、`placeId` を自然キーとする冪等トグル）。詳細スキーマ・設計判断は [`data-model.md`](./data-model.md) §1.9。

| # | 機能 | 優先度 | 備考 |
|---|------|--------|------|
| 10-1 | カフェを「行きたい」として保存 / 解除 | ○ | カフェ詳細画面のブックマークボタン。Firestore / SQLDelight に保存（既存 Repository 2 段構成踏襲） |
| 10-2 | 行きたい店のマップピン表示 | ○ | 既存 3 種ピン（訪問済み / 検索結果 / 好み一致）に 4 種目を追加。フィルタチップで表示切替。同一 placeId の競合は 訪問済み > 行きたい > 検索結果 の優先で 1 本表示 |
| 10-3 | 行きたい店リストの一覧表示 | ○ | マップのブックマークボタン → ハーフシート（savedAt 降順、タップでカフェ詳細、スワイプ解除）。記録作成時の自動解除は**しない**（記録がある店は「記録あり」バッジで表示解決。data-model.md §1.9） |

### 11. 広告（AdMob アダプティブバナー）

収益化手段として Google Mobile Ads SDK（AdMob）の**アダプティブバナー広告**を表示する（2026-07-14 grilling で確定）。Places API を主とする従量コストの回収が目的。

> **フォーマット変更の経緯（2026-07-14 同日）**: 当初は「UI に溶け込む」を優先しネイティブ広告で確定・実装したが、テスト広告の validator で **MediaView（最小 120×120pt）が必須アセット**と判明。コンパクト枠（ドロップダウン行 / 下部固定枠）に 120pt のメディアを組み込むとバナー（50〜60pt）より大きく悪目立ちし、「溶け込むからネイティブ」の前提が崩れたため、**全面アダプティブバナーに再編**（ユーザー確定）。経緯は implementation_note 2026-07-14。

**アーキテクチャ上の位置づけ**: 広告は表示の関心事として **`iosApp` の View 層で完結**させ、KMP 共通層・ViewModel には広告の概念を持ち込まない。Android（KMP 検証ターゲット、リリース対象外）には導入しない。将来の「広告非表示」IAP は**見据えない**（必要になった時点で後付けする。2026-07-14 判断）。

| # | 機能 | 優先度 | 備考 |
|---|------|--------|------|
| 11-1 | カフェ詳細のインライン広告 | ○ | 情報系セクション（カフェ情報 / 外部リンク / 営業時間）の後・コーヒー記録セクションの直前に 1 枠。**インラインアダプティブバナー**（maxHeight 制限付き） |

**確定仕様（全面共通）**:

- ロード失敗・オフライン時は**枠ごと畳む**（プレースホルダなし。補助機能の失敗は無音の既存方針と整合）
- クライアント側の自動リフレッシュ実装はしない（バナーの自動更新は AdMob コンソールのユニット設定に委ねる）
- `maxAdContentRating = G`（全年齢向けに制限）
- AdMob App ID / 広告ユニット ID（4 面 = 4 ユニット、**バナー用**）は Places キーと同じ経路（`Secrets.xcconfig` → `Info.plist`）で注入
- 広告の帰属表示・AdChoices はバナーでは Google レンダリングに内蔵されるため自前実装なし
- 配信地域は**日本のみ**（確定）→ GDPR 同意フォームは不要。**UMP のメッセージ表示 API はコードから呼ばない**（コンソール構成に挙動が依存し、ATT メッセージ構成時は GDPR 圏外でも自前プレプロンプトと二重表示になるため。UMP SDK 自体は Google Mobile Ads SDK の内部依存としてリンクされるのみ。EU 配信を始める場合は GDPR フォーム実装として再導入。implementation_note 2026-07-14）
- **Places 由来のデータ（店名・カテゴリ等）を広告リクエストのターゲティングシグナルに渡さない**（Google Maps Platform 規約遵守）

**未決事項**: 広告のプリロード / セッション内キャッシュ戦略の詳細は実装時に判断。

| 項目 | 要件 |
|------|------|
| パフォーマンス | 一覧表示は 60fps を維持する。画像はサムネイルキャッシュで遅延読み込み |
| アクセシビリティ | VoiceOver 対応・Dynamic Type 対応・最小タップ領域 44pt |
| オフライン | 完全オフライン動作可能（Firestore のオフライン永続化、ローカル SQLDelight） |

| API キー管理 | iOS は `Info.plist`、Android は `local.properties` → `BuildConfig` 経由で注入。いずれもリポジトリにコミットしない。漏洩対策は上記キー制限で担保 |

## データモデル概要

| エンティティ | 説明 | 関連 |
|-------------|------|------|
| `CoffeeRecord` | 1 杯のコーヒー記録（中心エンティティ） | `Cafe?`（埋め込み・任意）/ `Photo`（多）/ `TastingScores?`（埋め込み・任意） |
| `Cafe` | Places API 由来のカフェ情報スナップショット | `placeId` をキーに集約可能（`VisitedCafe`） |
| `TastingScores` | テイスティング 5 要素（甘味 / ボディ / 酸味 / 風味 / 後味） | `CoffeeRecord` に埋め込み（all-or-nothing） |
| `Photo` | 写真への参照 | Documents 配下からの相対ファイル名（クラウド同期対象外） |
| `VisitedCafe` | 同一カフェの記録を集計した表示用モデル | `cafe != null` の `CoffeeRecord` を `placeId` で集約 |
| `BeanProfile` | サーバー管理の豆ナレッジ（産地 / 品種 / 精製 / フレーバー） | 産地・品種のサジェスト、好み傾向の言語化に利用（フェーズ 12） |
| `SavedCafe` | 行きたい店（ウィッシュリスト）。§10 | `Cafe` を埋め込みスナップショット + 保存日時 + メモ。`placeId` が自然キー。詳細は [`data-model.md`](./data-model.md) §1.9 |

詳細なフィールド定義・SQLDelight / Firestore スキーマは [`data-model.md`](./data-model.md) を参照。`CoffeeItem` / `FoodItem` は廃止済み（§2 の設計変更ノート参照）。
