# バグ診断ループ

難しいバグのための規律。フェーズの省略は、省略する理由を明示できるときだけ。

コードベースを探索するときは、まず `docs/architecture.md` / `docs/data-model.md` で該当モジュールの構造を掴み、`docs/tasks/lessons.md` に同型バグの記録がないか確認する。

## Phase 1 — フィードバックループを作る

**この skill の本体はここ。** 残りは機械的な作業にすぎない。*このバグ*で赤くなる **tight** な pass/fail シグナルが 1 つあれば、原因は必ず見つかる — bisect も仮説検証も計装も、すべてそのシグナルを消費するだけ。逆にシグナルが無ければ、コードをいくら睨んでも救われない。

ここに不釣り合いなほどの労力を割く。**アグレッシブに。創造的に。諦めない。**

### ループの作り方 — おおよそこの順で試す

1. **失敗するテスト** — バグに届く seam ならどこでも。`commonTest` / `androidHostTest`（サブエージェント実行可）、`iosSimulatorArm64Test`（sandbox 制約により親が `DEVELOPER_DIR` 付きで実行）、iosApp 側は XCTest
2. **最小ハーネス** — 依存をモックした最小構成で、バグのコードパスを 1 関数呼び出しで叩く使い捨てテスト
3. **キャプチャしたデータのリプレイ** — 実際の Firestore ドキュメント / Places レスポンス / UIState をfixture 化し、該当コードパスに単体で流す
4. **プロパティ / ファズループ** — 「たまに出力がおかしい」系なら、ランダム入力 1000 件を回して失敗モードを探す
5. **bisect ハーネス** — 2 つの既知状態（コミット・データ・バージョン）の間で発生したなら、「状態 X で起動 → 判定」を自動化して `git bisect run` に載せる
6. **差分ループ** — 同じ入力を旧版 vs 新版（または 2 つの設定）に流して出力を diff する
7. **シミュレータ駆動** — `xcrun simctl` + XCUITest で UI を叩き、表示 / ログで assert する
8. **HITL bash スクリプト** — 最後の手段。人間の目視・操作（シミュレータでの UI 挙動確認など）が必要なら、`scripts/hitl-loop.template.sh` で*人間の側を*スクリプトが誘導する。キャプチャした回答がエージェントに戻る構造を保つ

正しいフィードバックループが作れれば、バグの 9 割は修正済みに等しい。

### ループを tight にする

ループは製品として扱い、一度作ったら磨く:

- **速くできるか？**（セットアップのキャッシュ、無関係な初期化のスキップ、テストスコープの絞り込み）
- **シグナルを鋭くできるか？**（「クラッシュしなかった」ではなく、具体的な症状そのものを assert する）
- **決定的にできるか？**（時刻の固定、RNG の seed 固定、ファイルシステム分離、ネットワーク遮断）

30 秒かかるフレーキーなループはループ無しと大差ない。2 秒で決定的なループは tight — デバッグの超能力になる。

### 非決定的なバグ

目標はクリーンな再現ではなく**再現率を上げる**こと。トリガーを 100 回ループ、並列化、負荷追加、タイミング窓の絞り込み、sleep 注入。再現率 50% のバグはデバッグできる。1% はできない — デバッグ可能になるまで率を上げ続ける。

### どうしてもループが作れないとき

止まって、そう明言する。試したことを列挙し、ユーザーに求める: (a) 再現する環境へのアクセス、(b) キャプチャ済み成果物（ログダンプ、クラッシュログ、タイムスタンプ付き画面録画）、(c) 一時的な計装追加の許可。**ループ無しで仮説フェーズに進まない。**

### 完了条件 — 赤くなれる tight なループ

Phase 1 の完了は、ループが **tight** かつ **red-capable** になったとき: スクリプトパス・テスト起動・CLI のいずれか **1 コマンド**を名指しでき、**すでに 1 回以上実行済み**（起動コマンドと出力を貼る）で、かつ:

- [ ] **Red-capable** — 実際のバグのコードパスを通り、**ユーザーの訴えた症状そのもの**を assert する。「エラー無く走る」ではなく、*このバグを捕まえられる*こと
- [ ] **決定的** — 毎回同じ判定（フレーキーなバグは上記の通り高再現率で固定）
- [ ] **速い** — 分単位でなく秒単位
- [ ] **エージェント単独で実行可能** — 無人で回せる。人間が挟まるのは `scripts/hitl-loop.template.sh` 経由のみ

このコマンドが存在する前に、コードを読んで理論を組み立てている自分に気づいたら**止まる — 仮説に直行するのが、この skill が防ぐ失敗そのもの。** red-capable なコマンド無くして Phase 2 無し。

## Phase 2 — 再現 + 最小化

ループを回し、赤くなるのを見る — バグが現れる。

確認:

- [ ] ループが**ユーザーの報告した**失敗モードを再現している — 近くにある別の失敗ではなく。バグ違いは修正違い
- [ ] 複数回の実行で再現する（非決定的なバグはデバッグに足る再現率で）
- [ ] 正確な症状（エラーメッセージ、誤った出力、遅いタイミング）をキャプチャ済みで、後のフェーズで修正の効果を検証できる

### 最小化

赤くなったら、**赤いまま残る最小シナリオ**まで再現を削る。入力・呼び出し元・設定・データ・手順を**1 つずつ**削り、削るたびにループを回す — 失敗に効いているものだけを残す。

理由: 最小の再現は Phase 3 の仮説空間を縮め（疑うべき可動部が減る）、Phase 5 のクリーンな回帰テストになる。

**残った要素すべてが失敗に効いている**（どれか 1 つ外すとループが緑になる）状態になったら完了。再現と最小化の両方が済むまで先に進まない。

## Phase 3 — 仮説

検証を始める前に、**ランク付きの仮説を 3〜5 個**出す。仮説 1 個での出発は、最初に思いついたもっともらしい案へのアンカリングを生む。

各仮説は**反証可能**であること: その仮説が立てる予測を書く。

> 型: 「もし <X> が原因なら、<Y を変える> とバグは消える / <Z を変える> と悪化する」

予測が書けない仮説は雰囲気にすぎない — 捨てるか研ぐ。

**検証前にランク付きリストをユーザーに見せる。** ドメイン知識で即座に並べ替えられること（「#3 は昨日変更をデプロイしたばかり」）や、検証済みで除外できる仮説を知っていることが多い。安いチェックポイントで大きな時間節約。ただしブロックはしない — ユーザーが離席中なら自分のランクで進む。

## Phase 4 — 計装

各プローブは Phase 3 の特定の予測に対応させる。**一度に変えるのは 1 変数。**

ツールの優先順:

1. **テスト seam での直接検証・デバッガ** — ブレークポイント 1 個はログ 10 個に勝る
2. **狙ったログ** — 仮説同士を区別できる境界に置く
3. 「全部ログして grep」は決してしない

**デバッグログには必ず一意のプレフィックスタグ**を付ける（例: `[DEBUG-a4f2]`）。後片付けが grep 1 回になる。タグ無しログは生き残り、タグ付きログは死ぬ。

**パフォーマンス退行の分岐**: 退行にはログはたいてい不適。ベースライン計測（タイミングハーネス、プロファイラ、クエリプラン）を確立してから bisect する。まず測り、修正はその後。

**SwiftUI の「重い / 落ちる」の分岐**: 症状がハングなら、まず**再評価が発散していないか**を数える。`Self._printChanges()` を疑う View の `body` 冒頭に置き、出力を `sort | uniq -c` で集計すると「何が」「何回」再評価を起こしたかがプロパティ名で出る。発散していれば引き金が名前で分かり、**ガードを入れて引き金が別プロパティへ移るかどうか**まで観測できる（移るなら症状に対処しているだけで原因に届いていない）。実機で Debug ビルドの stdout を取るなら `xcrun devicectl device process launch --device <id> --console <bundleID>` — **デバッガをアタッチしない**ので、ウォッチドッグを有効にしたまま観測できる。

**「Release / TestFlight でだけ落ちる」の分岐**: ビルド構成の差を探す前に、クラッシュログ（`.ips`）の **`bug_type` と `termination.namespace` を読む**。`bug_type: 309` / `namespace: FRONTBOARD` / `code: 0x8BADF00D` はクラッシュではなく**ウォッチドッグによるハングの強制終了**で、例外は発生していない。**Xcode から Run している間 iOS はウォッチドッグを無効化する**ため、同じハングが Debug でも起きていて殺されないだけ、という状態がある（ビルド構成は原因ではない）。この場合に探すのは「例外を投げる箇所」ではなく「**メインスレッドを継続的に焼いている処理**」。`WatchdogCPUStatistics` の CPU 使用率と `ProcessVisibility` も読む — `Background` なら CPU がスロットルされており、フォアグラウンドで間に合っていた処理がその瞬間だけ予算を超えている（lessons 2026-08-09 で 2 回誤診した型）。

## Phase 5 — 修正 + 回帰テスト

回帰テストは**修正の前に**書く — ただし**正しい seam** がある場合のみ。

正しい seam とは、テストが**実際のバグのパターン**を呼び出し元での発生形のまま行使できる場所。使える seam が浅すぎる（複数の呼び出し元が絡むバグに単一呼び出しのテスト、バグを起こした連鎖を再現できない単体テスト）なら、そこに置いた回帰テストは偽の安心を与える。

**正しい seam が無いなら、それ自体が発見。** 記録する。アーキテクチャがバグの封じ込めを妨げている — `docs/tasks.md` にバックログ化して Phase 6 に引き継ぐ。

正しい seam があるなら:

1. 最小化した再現を、その seam の失敗するテストにする
2. 失敗を見る
3. 修正を当てる
4. 成功を見る
5. Phase 1 のループを（最小化前の）元シナリオに対して回し直す

## Phase 6 — 後片付け + ポストモーテム

完了宣言の前に必須:

- [ ] 元の再現がもう再現しない（Phase 1 のループを回し直す）
- [ ] 回帰テストが通る（または seam 不在を記録済み）
- [ ] `[DEBUG-...]` 計装をすべて除去（プレフィックスを grep）
- [ ] 使い捨てハーネスを削除
- [ ] 正しかった仮説をコミットメッセージに書く — 次にデバッグする人が学べるように

**そして問う: 何があればこのバグを防げたか？** 汎用的な落とし穴なら `record-lesson` skill で lessons.md 記録 + 横断 sweep まで 1 セットでやり切る。要件未満の判断・経緯なら implementation_note へ。答えがアーキテクチャ変更（良いテスト seam が無い、呼び出し元の絡まり、隠れた結合）なら `docs/tasks.md` にバックログ化する。この振り返りは修正が入った**後**に行う — 着手時より今のほうが情報が多い。
