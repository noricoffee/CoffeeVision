# 教訓の記録 + 横展開点検

lessons への記録は**記録して終わりにしない**。2026-06-25 に記録した onDisappear バグは横展開点検をしなかったため、2026-07-03 に別 View（CafeDetailView）で同型バグとして再発した。この skill は「記録 → 即時 sweep → 結果も記録」を 1 セットの手順として強制する。

## 手順

### 1. 記録先を振り分ける

| 内容 | 記録先 |
|---|---|
| 汎用的な落とし穴・再発させたくないパターン | `docs/tasks/lessons.md`（この skill の対象） |
| 要件未満の実装判断・トレードオフ・経緯 | `docs/implementation_note.md` |
| 常時適用すべき規約に昇格できるもの | `.claude/rules/*.md`（lessons にも発生源として残す） |
| コードで表現できる事実 | docs に書かず、コード / テストに落とす |

### 2. lessons.md にエントリを書く

- **日付昇順・末尾追記**。当日の `## YYYY-MM-DD` セクションが無ければ作る
- エントリの型: **症状**（何がどう見えたか）→ **原因の構造**（なぜ起きるか。単発ミスか構造的か）→ **修正パターン**（コード例があれば具体的に）→ **教訓**（次回どう防ぐか）→ **発生源**（Phase / ファイル名）
- 既存エントリと同根なら、新規に書かず既存エントリへの参照を明記する（重複エントリを増やさない）

### 3. その場で横展開点検（sweep）する — 省略禁止

バグの「形」を grep 可能なパターンに落とし、リポジトリ全体を点検する。パターン設計の例:

- API の誤用形: `grep -rn "onDisappear" iosApp/ | grep -i "cancel"`（observation キャンセル）
- 型の危険な組み合わせ: `String(format` + Kotlin nullable 型のプロパティ名（NSNumber の %f 誤読）
- 禁止 API: `grep -rn "runCatching" shared/`（コルーチン内 CancellationException 握り潰し）
- 同一ファイル内に正しい使用例があるなら、それに揃っていない箇所を全 use で探す

grep で形にできない場合（設計パターン系）は、該当しうるファイル群（例: 全 `*ViewModelBridge.swift`）を列挙して目視点検する。

### 4. 点検結果をエントリに残す

- 「該当なし（grep パターンと対象範囲を明記）」または「該当あり → 修正済み / バックログ化」を必ず書く
- 該当ありで修正が非自明なら、その場で修正するか dispatch する。先送りする場合は `docs/tasks.md` に項目を立ててから終える

### 5. 仕上げの確認

- [ ] エントリに「症状 / 原因 / 修正パターン / 教訓 / 発生源」が揃っている
- [ ] sweep を実行し、結果（該当なし or 修正 or バックログ）をエントリに書いた
- [ ] rules / 正規 doc へ昇格すべき内容なら、同じ変更内で昇格まで行った（陳腐化防止。lessons 2026-06-16）
